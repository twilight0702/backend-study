### 「介绍一下你这个项目」：

> 这个项目是一个基于 Neo4j 图数据库的在线学习系统，我作为全栈开发参与从后端接口设计到前端交互实现。用户可以注册登录，浏览知识图谱，点击进入查看知识点内容，并根据知识点范围进行组卷测试。测试结果与错题会被记录，用户可以随时查看历史记录和错题重做。
> 
> 项目采用前后端分离架构，前端使用 Vue.js，后端基于 Spring Boot 提供 RESTful API。数据层使用 Neo4j 图数据库，设计了包括用户、知识点、试题等在内的图模型，并通过 Cypher 语言进行查询与关联分析。项目已部署在 GitHub 上并持续维护。

---

### 「这个项目有哪些亮点？」：

可以从以下几个方面总结亮点：

> 1. **图数据库建模与可视化**：我们使用 Neo4j 替代传统关系型数据库，构建了可视化的知识图谱，前端通过物理引擎展示知识点之间的联系，用户可以交互式探索知识结构。
>     
> 2. **个性化智能组卷**：用户可以按知识点选择题目范围，系统从图数据库中动态抽取相关试题，构建个性化测试卷，提升学习效率。
>     
> 3. **错题重做机制与学习数据分析**：用户的测试行为、答题记录以图结构存储，便于从知识点维度分析薄弱项，辅助学习路径优化。
>     
> 4. **前后端分离 + 全栈实现**：我负责前后端主要功能开发，从 Vue 前端界面交互到 Spring Boot 后端接口再到 Neo4j 数据查询，实现完整闭环的用户体验。
>

这个项目其实是我第一次完整参与一个多人协作、前后端分离的全栈项目，也是第一次接触非关系型数据库。之前课程设计一般都是写单文件的 Java，没有接触 SpringBoot、Maven、前后端交互这些框架和工程化流程。
**最开始的难点**主要有两个方面：

- 二是 **SpringBoot 和 Neo4j 的整合**，查不到数据或连接不上图数据库，不知道问题在哪。

我的解决方法是：

- 在调试过程中，通过对比参考 Demo 项目，一步步拆解功能，从连接数据库到写第一个 REST 接口，逐步搭建后端框架。
    
- 同时，边做边总结，把遇到的问题和解决方案都记录下来，也帮助团队后期踩坑少很多。
    

通过这次项目，我对 Java 工程开发、Maven 项目管理、图数据库建模、前后端接口交互这些内容有了比较系统的掌握，也更熟悉了如何独立从 0 搭建一个完整项目。

#### 示例难点 1：图数据库建模与高效查询

> **难点**：Neo4j 的数据建模思路与传统关系型数据库不同，如何合理设计节点和关系结构，并优化 Cypher 查询，是一开始面临的挑战。  
> **解决方案**：我们分析知识图谱的使用场景，把 `知识点`、`用户`、`试题`等建为节点，建立“包含”、“答过”、“错过”等语义关系；并通过使用索引、限制查询深度等手段优化 Cypher 查询效率。后期使用 Profile 命令分析查询计划进一步提升性能。

#### 示例难点 2：前后端接口设计与数据交互

> **难点**：图数据库返回的是嵌套结构，如何让前端方便地处理这些复杂结构，同时保持接口简洁，是开发中一个关键问题。  
> **解决方案**：后端封装了统一的 DTO（数据传输对象），对查询结果进行结构转换，返回前端易处理的 JSON 数据结构；前端使用 Vue 的组件化机制封装图谱节点、边和交互操作，提升开发效率和代码复用性。

#### 示例难点 3：知识图谱的动态可视化

> **难点**：如何用前端框架动态渲染出用户可交互的知识图谱，并确保性能与体验良好。  
> **解决方案**：前端使用如 Force-Graph、ECharts 等 JS 图形库，通过后端接口获取图数据并动态渲染，实现节点拖拽、放缩、点击高亮等功能。




#### 一、常见的 SpringBoot 注解我都使用过，主要包括以下几类：

用过`@Configuration` 配置neo4j数据库相关，还有`@Component` / `@Service` / `@Repository` / `@Controller`：将类交给 Spring 容器管理

##### 1. **SpringBoot 启动相关**

- `@SpringBootApplication`：这是组合注解，包含：
    
    - `@Configuration`：声明配置类
        
    - `@EnableAutoConfiguration`：启用 Spring Boot 自动配置机制
        
    - `@ComponentScan`：自动扫描当前包及子包的组件
        

> **原理理解**：`@EnableAutoConfiguration` 底层通过 `spring.factories` 机制加载自动配置类（使用 `@Conditional` 条件注解控制生效与否），实现“约定优于配置”。

---

##### 2. **依赖注入与 Bean 管理**

- `@Component` / `@Service` / `@Repository` / `@Controller`：将类交给 Spring 容器管理
    
- `@Autowired`：注入 Bean（也可以使用 `@Resource`）
    
- `@Bean`：手动注册 Bean 到容器中
    

> **原理理解**：基于 Spring 的 IOC 容器，启动时通过扫描带注解的类并注册到 BeanDefinition 中，创建 Bean 实例时按依赖注入规则装配。

---

##### 3. **请求处理相关（SpringMVC）**

- `@RestController`：返回 JSON 的控制器，等同于 `@Controller + @ResponseBody`
    
- `@RequestMapping`、`@GetMapping`、`@PostMapping`：定义接口路由
    
- `@PathVariable`、`@RequestParam`、`@RequestBody`：获取请求数据
    
- `@ResponseBody`：方法返回值自动序列化为 JSON
    

> **原理理解**：使用 HandlerMapping 匹配 URL 与方法，参数解析器从请求中提取参数，返回值由 HttpMessageConverter 转为 JSON 响应。

---

##### 4. **配置与属性绑定**

- `@ConfigurationProperties`：将配置文件的值绑定到 Java 对象
    
- `@Value`：注入单个配置值
    
- `@EnableConfigurationProperties`：启用配置类
    

---

##### 5. **事务控制**

- `@Transactional`：声明方法/类启用事务控制，支持回滚、传播机制等
    

> **原理理解**：通过 AOP 代理，在方法调用前后加事务管理逻辑。

---

##### 6. **开发调试**

- `@Slf4j`（Lombok）：自动注入日志对象，方便打印调试日志
    

---

#### 二、我对 SpringBoot 的底层机制有一定了解，比如：

- **自动配置原理**：基于 `spring.factories` 机制，读取 `META-INF/spring.factories` 配置文件，自动装配指定类。
    
- **依赖注入原理**：基于 IOC 容器，将类注册为 Bean，并通过反射或构造器方式注入依赖。
    
- **组件扫描机制**：`@ComponentScan` 会扫描指定包路径下的注解类，注册到容器中。
    
- **AOP 原理（如事务控制）**：使用动态代理或 CGLIB，对方法前后织入切面逻辑。
    

---

### ✅ 总结性回答（可直接用于面试）：

> 在项目中我使用了很多 SpringBoot 注解，比如 `@SpringBootApplication`、`@RestController`、`@Autowired`、`@Transactional` 等，我也了解它们的原理，比如自动配置是通过 `spring.factories` 和条件注解控制的，依赖注入是基于 IOC 容器管理 Bean 实例的，事务注解是通过 AOP 动态代理实现的。

### 1. **项目简介**（介绍功能 + 技术 + 场景）：

> 这是我独立开发的一款 AI 聊天机器人，主要特点是具备**长期记忆**、**上下文理解能力**以及**多角色切换机制**，目标是实现更自然、连贯的虚拟陪伴对话体验。  
> 技术上，我使用了 Python 语言，融合 DeepSeek API 提供多角色大模型对话，结合本地部署的 Ollama 模型和 Qdrant 向量数据库，实现 RAG（检索增强生成）架构，增强语义理解与长期记忆能力。此外，通过 SQLite 并设计三层记忆池的结构，管理用户数据和记忆，实现对话记录、用户偏好等内容的持久化。

---

### 2. **项目亮点**（结合技术难度 + 用户体验）：

> - **自定义记忆体系设计**：引入“临时缓冲区、中层记忆、长期记忆”三级记忆结构，使机器人能根据对话情况动态生成摘要、管理上下文，并根据用户历史持续调整对话风格。
>     
> - **RAG 架构语义增强**：利用本地部署模型 + Qdrant 向量库进行语义检索，提高机器人对用户上下文的响应准确性，解决了“长文本丢失上下文”问题。
>     
> - **角色切换与人设管理**：用户可以动态热切换角色，通过 prompt 管理配置，支持多种人格与语气的 AI 对话，增强用户沉浸感。
>     
> - **一次多轮输入、自然分段回复**：优化输出逻辑，支持用户一次输入多条问题，AI 分段作答，模拟更真实的聊天体验。
>     

---

### 3. **项目难点与解决方案**

#### ① **记忆系统的分层设计和管理**

> 起初直接存储全部历史对话，导致上下文混乱、响应不准确。  
> 后来设计了**三层记忆结构**：
> 
> - **临时缓冲区**：缓存最近几轮对话
>     
> - **中层记忆**：筛选并摘要有价值内容
>     
> - **长期记忆**：存储全部摘要，定期压缩  
>     通过结合关键词匹配和语义相似度，自动提取历史信息参与生成，提高了连贯性和用户定制性。
>     

#### ② **RAG 检索机制实现**

> 采用 Ollama 本地部署模型做向量化处理，Qdrant 做向量存储，Chat 过程中通过语义召回补充上下文。  
> 初期遇到性能问题，通过缓存策略、批量向量查询等手段优化性能。

#### ③ **角色 prompt 热切换机制**

> 支持用户在聊天中即时切换“人设”，并实时刷新上下文 prompt。解决过程涉及对 prompt 管理结构进行模块化封装、支持热加载配置。
