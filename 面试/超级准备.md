## MySQL优化

对应简历：- 使用MySQL数据库存储用户数据，**使用user_id分库分表**，建立如 `user_id + question_id` **联合索引**，配合覆盖索引优化分页查询与筛选效率，降低用户错题本等高频接口响应时间

最开始我的设想是使用功能分表，比如说用户账密信息、个人信息区、用户错题区，将user_id
作为每个表的主键，建立主键索引，进行存储和增删查改。对于前两个表没有很大问题。但是当用户数增加或者用户活动增多的时候，这个用户错题区会变得很庞大，每一个用户都有大量的错题数据，又有着大量的用户，这势必会降低数据库访问的效率，进而大幅影响整个系统的运作。基于这个考虑，将错题表 按 user_id 进行哈希，把数据分散成为多张表，并对`user_id + question_id`建立联合索引。本系统中的题目数据存储于图数据库，MySQL中没有存储具体题目信息，该操作也就意味这可以一步到位查询目标数据无需回表。以上设计相较于最初的设计在性能方面有巨大提升。

## Redis 缓存

简历： -使用 **Redis 缓存**热点知识点、题库和用户学习数据等高频数据，结合布隆过滤器、防击穿锁及过期随机化策略，有效防止缓存穿透、击穿与雪崩，并通过延迟双删或Binlog监听确保缓存与数据库一致性


- **热点数据**：知识点、题库内容、用户学习进度等属于访问频率高、读取多且更新相对较少的数据。
- **目的**：减少数据库压力，降低响应延迟，提高系统吞吐量和用户体验。

### 2.1 缓存穿透（Cache Penetration）

- **问题**：客户端请求一个数据库和缓存中都不存在的key（例如非法请求），导致每次都穿透缓存直接查询数据库，造成数据库压力。
- **解决策略**：
    - **布隆过滤器**（Bloom Filter）：
        - 预先将所有合法的知识点ID、题库ID、用户ID等加入布隆过滤器。
        - 查询时先通过布隆过滤器判断key是否存在，大概率过滤非法请求。
        - 优点：内存占用小，查询速度快，避免大量无效请求访问数据库。
    - **缓存空结果**：
        - 对于数据库中确实不存在的key，可以缓存空值或特殊标记，设置较短的过期时间，避免频繁查询。

---

### 2.2 缓存击穿（Cache Breakdown）

- **问题**：热点key突然失效时，大量请求同时查询数据库，导致数据库瞬时压力过大。
- **解决策略**：
    - **互斥锁（防击穿锁）**
        - 当缓存失效时，只有第一个请求允许查询数据库并重建缓存，其它请求等待锁释放。
        - 实现方式如Redis分布式锁（SETNX + 过期时间），或基于本地锁。
    - **预防性缓存刷新**：
        - 设置合理过期时间，提前异步刷新缓存，避免缓存同时过期。
    - **热点缓存永不过期**：
        - 对极热点数据采用永不过期策略，结合后台定时更新。

---

### 2.3 缓存雪崩（Cache Avalanche）

- **问题**：大量缓存key在同一时间失效，导致请求集中打到数据库。或者数据库服务崩溃
- **解决策略**：
    - **过期时间随机化**：
        - 给缓存设置基础过期时间加随机值，避免同一时间大量缓存同时过期。
    - **多级缓存**：
        - 结合本地缓存和分布式缓存，降低对单一Redis实例压力。
    - **限流降级**：
        - 在缓存失效时对请求进行限流，保证数据库可用。
    - 利用redis集群提高服务的可用性
    - 给缓存业务添加降级限流策略

---

### 3. 缓存与数据库一致性保证

### 3.1 缓存更新策略挑战

- 缓存和数据库更新存在时序问题，可能出现**缓存脏数据**或**缓存雪崩**。
    
- 常见更新场景包括用户答题提交导致用户学习数据和错题本变化。
    

### 3.2 解决方案

#### 方案一：延迟双删策略

- **操作流程**：
    
    1. 修改数据库后，立即删除缓存。
        
    2. 等待一段延迟（如几百毫秒），再次删除缓存，防止数据库操作和缓存删除操作存在延迟导致的脏数据。
        
- **优点**：简单易实现，适合大部分业务场景。
    
- **缺点**：无法完全解决分布式环境下多节点并发写带来的竞态问题。
    

#### 方案二：基于数据库Binlog监听同步缓存

- **操作流程**：
    
    - 通过监听数据库的Binlog日志（如使用Canal、Debezium），捕获数据库变更事件。
        
    - 实时同步或异步更新Redis缓存，保持缓存和数据库高度一致。
        
- **优点**：保证强一致性，适合读写频繁且数据一致性要求高的业务。
    
- **缺点**：实现复杂度高，增加系统组件和维护成本。

## 消息队列

简历：- 利用RabbitMQ异步处理高耗时任务，配合消息确认、死信队列及重试机制保障消息可靠性，通过幂等设计防止重复消费，提升系统性能、并发能力及稳定性

出题和判题部分操作可能耗时较长，直接使用同步的http请求可能导致请求响应延迟，影响用户体验和系统吞吐量。因此我考虑引入RabbitMQ消息队列异步处理

- **生产者（Producer）**：将高耗时任务封装成消息发送到 RabbitMQ 队列。
    
- **消息队列（Broker）**：负责消息存储和转发，解耦生产者和消费者。
    
- **消费者（Consumer）**：异步接收并执行任务，完成后反馈结果。

- RabbitMQ 的消费者模型是 **推模式**（Push-based），Broker 会 **主动**将消息 **推送** 给消费者，而不是消费者主动去拉取消息。
- 当消费者与 RabbitMQ 建立连接并订阅队列后，RabbitMQ 会根据消费者的处理能力（通过 QoS 设置）推送消息。
- 这种机制保证消息能实时传递给消费者，延迟较低。

消息确认和死信队列：
- 消费者在接收到消息后，处理业务逻辑，处理完成后发送确认（ACK）给 RabbitMQ。如果处理失败，可以拒绝（NACK）或不确认（不发送 ACK），消息会被重新投递或进入死信队列，同时设置重试机制，消息消费失败后进入延迟队列，经过一定时间后自动回到主队列重试，而死信队列部分，消息超时（TTL）未消费，消息在重试机制中达到最大重试次数，都会进入死信队列，避免无限重试阻塞主队列。

在使用消息队列（如RabbitMQ）时，由于网络异常、消费者宕机、消息确认机制等原因，**同一条消息可能被多次投递给消费者**，导致消费者重复处理同一业务请求。如果业务处理不是幂等的，就会出现数据重复、状态异常等问题。

因此，必须设计幂等机制，确保**无论消息被消费多少次，最终业务状态保持一致，且副作用只发生一次**。

---

## 2. 幂等设计核心思想

**幂等性**是指对同一请求执行一次或多次，结果相同且业务状态不变。

实现幂等主要思路是通过“**唯一标识 + 去重校验**”来保证同一消息仅被处理一次。

---

## 3. 常用幂等设计方法

### 3.1 业务唯一标识（ID）

- 每条消息带有唯一的业务标识，如消息ID、订单号、流水号等。
    
- 消费者在处理前，先判断该业务ID是否已被处理过。
    

### 3.2 去重校验存储

- **数据库去重**：
    
    - 在业务数据表中设计唯一约束（唯一索引），保证相同业务ID只能写入一次。
        
    - 通过捕获唯一索引冲突异常避免重复插入。
        
- **缓存去重**：
    
    - 使用Redis等缓存存储已处理的业务ID，消费前先查询。
        
    - 处理完成后，将ID写入缓存，设置过期时间防止缓存膨胀。
        

### 3.3 消费日志记录

- 在独立表中记录每条消息的处理状态（已处理、处理中、失败）。
    
- 消费时先查询日志表，若已处理则跳过，未处理则执行处理并更新状态。
    

---

## 4. 典型流程示例

1. 消费者收到消息，解析出唯一业务ID。
    
2. 查询数据库或缓存，判断该ID是否已处理：
    
    - 已处理 → 跳过，直接确认消息。
        
    - 未处理 → 执行业务逻辑。
        
3. 业务逻辑执行成功后：
    
    - 将业务ID写入数据库或缓存，标记已处理。
        
    - 发送消息确认（ACK）。
        
4. 若业务执行失败，则拒绝消息或不确认，让消息重新入队。

## Security+JWT

#### 2.1 用户登录认证

- 用户通过登录接口提交用户名和密码。
    
- Spring Security 认证管理器验证用户身份（如查询数据库验证密码）。
    
- 验证成功后，系统生成包含用户身份信息及权限信息的 JWT 令牌。
    
- JWT 令牌返回给客户端，客户端保存（通常放在 HTTP Header 的 Authorization 字段）。
    

#### 2.2 请求鉴权

- 客户端每次请求时，在请求头带上 JWT。
    
- Spring Security 通过自定义过滤器解析 JWT，验证签名合法性和有效期。
    
- 验证通过后，将用户信息封装为 `Authentication` 对象，存入 `SecurityContext`。
    
- 后续业务逻辑通过 Spring Security 的权限注解（如 `@PreAuthorize`）或访问控制规则进行权限校验。

- **无状态**：服务器不保存任何登录状态，JWT 自包含认证信息，降低服务器存储压力。
    
- **跨服务统一**：各微服务只需验证 JWT，无需共享 Session，简化分布式系统设计。
    
- **可扩展性强**：新服务只需集成 JWT 验证逻辑即可接入权限体系。
    
- **安全性**：JWT 使用签名（HMAC 或非对称加密）防止篡改，且支持设置过期时间，增强安全。

## 简介

忆伴是聊天机器人项目，该项目构建了一个具备长期记忆和上下文理解能力的智能聊天机器人，支持多角色切换，提升对话自然度和智能水平。
在这个项目中我主要负责了后端的设计和实现，利用异步编程（asyncio、队列）和锁机制，提升多轮对话中大模型调用的效率和线程安全性。
采用Rag架构，结合Ollama文本向量化模型和Qdrant向量数据库，实现本地语义检索，提升模型对上下文和历史信息的理解能力。
同时设计了分层记忆体系（临时缓冲、中层记忆、长期记忆），支持上下文摘要和动态召回，增强对话连贯性。
实现了角色prompt的热加载和缓存，支持多角色动态切换，满足不同场景的陪伴需求。
优化聊天响应逻辑，支持多条输入接收和自然分段回复，模拟真人风格，用户体验良好。

## 关于RAG？

**RAG（Retrieval-Augmented Generation）检索增强生成** 是一种结合了**检索（Retrieval）** 和 **生成（Generation）** 的模型架构，旨在提升生成模型的能力，尤其是在回答问题或生成长文本时，能够借助外部知识库提供更多准确、全面的信息。RAG模型的核心思想是：在生成答案时，通过从外部信息源（如文档、数据库或互联网）检索相关内容，然后将检索到的信息与生成模型结合，生成更高质量的输出。

## 责任链设计

最开始我们的程序是用一个单一的模块进行用户消息处理，然后返回，各种处理逻辑都耦合在一起，不方便进行测试修改，因此想到了使用责任链进行设计优化

具体是类似工作流的设计，将原本耦合的处理逻辑拆分成一个个独立的处理模块，模块之间没有直接通信，可以直接修改单一模块而不影响其他模块的实现。同时定义了一个配置类，用于定义整个处理流程，配置模块处理的先后关系。接收到前端的http请求的时候，从请求中解析出用户的聊天请求数据，包装进定义好的上下文类实例中，将这个上下文类的实例传入控制器，控制器按照配置好的顺序，把上下文类实例在各个责任链处理模块中传递，最后从这个上下文类实例中解析出给用户的回复信息，返回给前端

这样的优化使得流程修改和单一模块修改变得容易。比如说在开发中，原本是没有情景处理模块的，然后临时需要在其中添加相关逻辑，以往需要在复杂的函数中寻找相关内容进行判断修改，现在只需要在流程中添加一个模块，单独写一个处理模块类就好了


只能单流程？
不是的，我们整体流程分成两步骤，一步是聊天结果的回复生成，第二步是判断回复中是否含有特殊标记需要处理，每一步都有多个处理模块。在上下文中有12步骤是否完成的标记。虽然流程定义是单流程，但是实际处理的时候，第一步某一处理模块中，判定为第一步完成，将对应标记设计为完成，配置类就会自动读取然后跳过第一步的后续处理模块，来到第二步


## 大模型封装

这里我负责编写了一个大模型调用类，实际处理流程中无需关系使用的是什么模型，只需要传入需要AI处理的文本和提示词，就可以获取到需要的回复。具体这个类负责读取用户配置文件中的数据，比如说base-url，key等等，然后构建请求，调用对应官方的api，获取回复。对于多模态数据，应公司要求是强制使用了阿里云百炼的api，其余文本消息的回复是适配了所有Openai格式的api接口

## RAG

这里是使用了RagFlow框架。由于这个只能使用python编写，这里具体实现是其他公司成员用Python编写了RagFlow框架的具体实现，单独部署，后端Java程序这里通过向它发送http请求获取需要的知识库数据。（同时python程序中使用了FAISS建立索引，实现查询）

## IPC

这里前端部分是使用electron+vue，先定义好预加载脚本，用户点击进入店铺，electron框架开启一个渲染线程，加载对应的平台的客服页面，同时注入这个预加载脚本。之后这个脚本建立主进程和渲染进程之间的通信通道，同时通过判断这个页面的url，根据url再注入对应平台的处理脚本，之后脚本捕获页面元素数据，获得数据，通过IPC通信给主进程，主进程根据消息判断，构建给后端的信息，向后端发送http请求，获取回复后自动发送

## 单例模式

**定义**：保证一个类只有一个实例，并提供一个全局访问点。

**特点**：

- 构造函数私有化，防止外部直接创建对象
    
- 通过静态方法或属性返回唯一实例
    
- 确保全局范围内只有一个对象实例，节省资源
    

**应用场景**：

- 需要全局共享的资源，如配置管理器、线程池、数据库连接池等

## 工厂模式

工厂模式通过定义一个**工厂类**，根据传入的参数决定创建哪个具体的产品类对象，**调用者无需关心具体创建过程，只关心返回的接口或抽象类**。
