# 1 异常处理的目的

异常处理的主要目的有三点：

1. **保障系统健壮性**：即使出现错误，系统仍然可以稳定运行，不崩溃。
2. **提供准确的问题反馈**：让开发者/用户知道错误发生在哪里，是什么类型的错误。
3. **避免数据污染或进一步扩散**：错误若不处理，可能导致下游逻辑出错或错误结果写入数据库。

# 2 异常处理规范

> 什么时候try catch？如何判断或者知道什么是正确的？
## 2.1 异常分类

### 2.1.1 业务异常（可预期）

- **定义**：业务规则检查失败，不是程序错误。
- **示例**：
    - 参数不合法
    - 业务状态冲突（如订单已取消不能支付）
    - 数据不存在
- **做法**：
    - 定义自定义异常类，继承 `RuntimeException`（便于事务回滚）。
    - 在业务方法中直接 `throw`，**不要** `try-catch` 再原样抛出。
    - 交给全局异常处理器统一转为友好的响应。

```java
public class BadRequestException extends RuntimeException {
    public BadRequestException(String message) { super(message); }
}
public class NotFoundException extends RuntimeException {
    public NotFoundException(String message) { super(message); }
}
```

### 2.1.2 系统异常（不可预期）

- **定义**：代码 bug、第三方系统异常、数据库连接失败等。
- **示例**：
    - `NullPointerException`
    - `SQLException`
    - 第三方 API 报错
- **做法**：
    - 不在业务代码中 catch，直接抛出。
    - 全局异常处理器记录详细日志（堆栈），返回通用错误信息（避免泄露内部细节）。

---

### 2.1.3 受检异常

- **定义**：Java 编译器要求必须处理的异常（`IOException`、`ParseException`）。
- **做法**：
    - 业务层捕获后，转成自定义运行时异常抛出。
    - 或在工具层包装成 `RuntimeException`。

---

## 2.2 异常处理原则

1. **能预判的业务异常 → 直接抛自定义异常**
2. **非预期异常 → 让全局异常处理器兜底**
3. **禁止依赖 `Exception.getMessage()` 做类型判断**
    - 用 `instanceof` 判断异常类型更稳。
4. **统一异常返回结构**
    - HTTP 状态码 + 错误码 + 错误信息 + 时间戳
5. **只在需要的地方 try-catch**
    - 有降级逻辑、补充日志、或必须屏蔽底层异常细节时才 catch。

## 2.3 全局异常处理器示例

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BadRequestException.class)
    public ResponseEntity<ErrorResponse> handleBadRequest(BadRequestException ex) {
        return ResponseEntity
                .status(HttpStatus.BAD_REQUEST)
                .body(ErrorResponse.of(4001, ex.getMessage()));
    }

    @ExceptionHandler(NotFoundException.class)
    public ResponseEntity<ErrorResponse> handleNotFound(NotFoundException ex) {
        return ResponseEntity
                .status(HttpStatus.NOT_FOUND)
                .body(ErrorResponse.of(4041, ex.getMessage()));
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErrorResponse> handleOtherExceptions(Exception ex) {
        log.error("系统异常", ex);
        return ResponseEntity
                .status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(ErrorResponse.of(5000, "系统开小差了，请稍后重试"));
    }
}
```

---

## 2.4 异常返回统一结构

```java
@Data
@AllArgsConstructor
@NoArgsConstructor
public class ErrorResponse {
    private int code;          // 错误码
    private String message;    // 错误信息
    private long timestamp;    // 时间戳

    public static ErrorResponse of(int code, String message) {
        return new ErrorResponse(code, message, System.currentTimeMillis());
    }
}
```

## 2.5 推荐工程约定

- **异常类分包管理**
    
    ```
    com.example.exception
        ├── BadRequestException.java
        ├── NotFoundException.java
        ├── ForbiddenException.java
        └── GlobalExceptionHandler.java
    ```
    
- **错误码规范**
    - 4xxx → 业务异常
    - 5xxx → 系统异常
    - 每个模块可分配一个错误码段。
- **日志规范**
    - 业务异常用 `warn`
    - 系统异常用 `error`（带堆栈）

---

## 2.6 总结流程图

```
业务代码 → 
    可预期错误 → throw 业务异常 → 全局异常处理器 → 返回业务错误
    不可预期错误 → 抛出系统异常 → 全局异常处理器 → 返回系统错误
```

# 3 异常处理边界
## 3.1 异常处理的边界思考

我们不能也不应该对一切“可能出错”的情况都做异常处理，否则代码会极度冗余、开发效率极低，还可能掩盖真正的 bug。

所以需要 **划清边界：什么值得处理？什么可以信任？**

### 3.1.1 应该处理的异常（建议兜底）：

- **外部输入不合法**（用户参数校验）→ controller 层处理
- **网络/数据库连接类异常**（不可控）→ 全局异常处理兜底
- **可能破坏系统状态的异常**（如事务中某个步骤失败）→ service 层捕获并回滚
- **你依赖的外部服务/组件可能不稳定** → 尽量 try-catch 包裹
### 3.1.2 可选处理的异常（视情况而定）：

- **数据库中非预期的数据（例如缺少题号2）**
    - 如果**该数据是用户可修改的/不受你控制**，应验证。
    - 如果**该数据是只读配置/初始化固定的**，可以不做检测，但做好启动时的校验或监控。

## 3.2 你提到的具体场景分析

> **你现在从数据库中获取测评题目的分数信息，按题号降序排列，理论上应该是一系列连续的 list，如 1,2,3...。那是否需要检查这种连续性？**

### 3.2.1 判断依据是：**这些数据是固定配置，还是用户行为会影响它？**

- **如果这些题目是由你方后台配置/初始化固定的：**
    
    - 建议在**系统启动时或配置上传时校验一次即可**（如每个问卷题号是否连续、分数是否为空等），避免每次请求都检查。
    - **运行期无需重复检测**，否则就是冗余检查。
        
- ⚠️ **如果这些题目是用户行为或运营人员经常变动的数据：**
    
    - 那么就需要在运行期加一些基础校验（如是否为空、是否有重复题号、是否连续）。
    - 否则一旦配错就会造成严重后果（如测评结果错误）。
        

## 3.3 最佳实践建议

### 3.3.1 **分层处理异常**

| 层级         | 异常类型          | 建议做法                                       |
| ---------- | ------------- | ------------------------------------------ |
| Controller | 用户参数错误        | 使用 `@Validated` + `@ControllerAdvice` 统一处理 |
| Service    | 核心业务异常，如数据不完整 | 抛出自定义业务异常 `BusinessException`，被全局异常处理器捕获   |
| Repository | 数据库操作失败       | 依赖 Spring 异常封装，通常无需 try-catch，除非需要自定义处理    |
| 启动/初始化     | 固定配置是否符合要求    | 初始化阶段加断言或日志提示，避免运行期故障                      |

### 3.3.2 **业务异常 vs 技术异常 分离**

- **技术异常**：如数据库连接失败，属于非业务可控范围 → 日志记录 + 500 响应
- **业务异常**：如测评题目不连续 → 抛出 `BusinessException("测评题目配置错误")`，前端可识别为 400 类错误

### 3.3.3 **数据完整性靠流程/工具保障，而不是业务代码重复检测**

- 用数据库约束（如唯一索引、非空）
- 用单元测试/Mock 数据检测流程
- 配置中心做数据检查

## 3.4 你是否需要现在加这类数据完整性检查？

结论：**视数据来源决定是否运行期检查**。

|情况|是否建议加检查|检查时机|
|---|---|---|
|测评分数数据为后台配置，理论不会变|❌ 不建议每次都检查|✅ 启动时验证一次|
|测评分数数据由非技术人员频繁改动（如 Excel 导入）|✅ 应该加检查|✅ 上传时 + 运行时兜底|
|测评过程或数据量很大、异常后果严重|✅ 可加断言|✅ 运行期保障结果正确性|

## 3.5 一句话总结

> 异常检测的关键在于：**信任链边界在哪里？哪些数据是可靠的，哪些是不可靠的？**  
> 对于不可靠来源的数据（如用户上传、动态配置），需要防御式编程；对于你控制范围内的固定数据（如初始化脚本），只需在适当时机校验一次即可，不必运行期重复校验。

如果你能判断测评题目列表为只读配置数据，那么无需每次都判断是否按题号连续；而是提供一处工具类或脚本，在系统启动或配置变更时做一次检查即可。
